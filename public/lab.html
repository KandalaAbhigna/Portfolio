Scaling T20 Predictor from ~4,500 to 100,000 assets

What breaks first, what I would change, and in what order. A design proposal, clearly separated from what is built.

Format
Design exercise, not a description of production
Themes
Queues · horizontal scaling · partitioning · caching · rate limiting · retries · observability

The premise

T20 Predictor today scores about 4,500 tickers with five sequential ECS tasks. That design is right for its size: one container per stage, a state machine, a nightly schedule. This page is a design exercise, not a description of what exists. The question is what breaks first at 100,000 assets, and what I would change, in order.

What breaks first

  1. The vendor rate limit. At 150 requests per minute, 100,000 daily downloads take over 11 hours if done naively. The download stage becomes the whole day.
  2. Single-task memory. The dataset build already needs 8 GB for 4,500 tickers. A 22× dataset in one process is not an option.
  3. All-or-nothing runs. One bad ticker fails a stage; a failed stage fails the run; the dashboard shows nothing new. At 100,000 assets, some ticker is always bad.
  4. The API reading storage. Precomputed JSON still means a file read per request. With more users and bigger payloads, the API needs a real cache.

Proposed architecture

1. Partition and queue

The scheduler no longer runs a stage; it enqueues work. A partitioner splits 100,000 assets into roughly 400 jobs of 250 tickers and puts each on an SQS queue. Workers pull jobs, so the number of workers, not the size of the universe, sets the wall-clock time.

2. Horizontal workers with a shared budget

An ECS service of identical workers scales on queue depth. Vendor calls go through a token bucket in Redis so the fleet as a whole respects the rate limit; if the vendor allows multiple keys or a bulk endpoint, the bucket grows. Workers are stateless and idempotent: reprocessing a job overwrites the same partition path in S3, so a retry is always safe.

3. Retries, backoff, and dead letters

SQS visibility timeout handles crashed workers; exponential backoff with jitter handles vendor throttling; after three failed attempts a message moves to a dead-letter queue and raises an alarm. The run completes with, say, 99.8% coverage and a list of what is missing, instead of failing outright.

4. Partitioned storage

S3 paths keyed by date and partition; feature and prediction tables partitioned by date so daily writes never rewrite history and queries for "today" touch one partition. Object storage holds the wide data; the relational database holds what the API serves.

5. Cache in front of the API

The stats stage writes the finished dashboard views into Redis with a TTL past the next run. The API reads the cache and never touches S3 or the database on the request path. An API gateway in front adds auth, per-client rate limiting, and backpressure (429s) instead of letting a burst reach the origin.

6. Observability

Every job emits a run ID, partition ID, duration, and row count. Alarms on: queue age, dead-letter depth, coverage below 99%, and "no new predictions by 07:00." A single status endpoint reports the last successful run so stale data is visible, which was the first thing missing in the current system.

Tradeoffs I would accept

  • Eventual consistency. Partitions finish at different times. The dashboard shows a run as complete only when the stats stage has published, not when the first partition lands.
  • More moving parts. Queues, a cache, and a worker fleet are more to operate than five tasks. Worth it at 100,000 assets; not worth it at 4,500, which is why the current design is the right one for now.
  • Cost shape. Fargate workers scale to zero between runs, so cost tracks work done. The always-on pieces are Redis and the gateway; both are small.
