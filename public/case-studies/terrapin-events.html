Terrapin Events — Campus Event Management System

API design, authentication, testing discipline, containerization, and a Kubernetes deployment that a team can run.

Stack
FastAPI, React, TypeScript, MongoDB, JWT, Pytest, Vitest, Docker, Kubernetes, GitHub Actions

Problem

Campus events at a large university are coordinated over email, forms, and spreadsheets. Organizers do not know if an event has been approved, participants do not know if they got a seat, and nobody has a reliable count at the door. Terrapin Events replaces that with one system: organizers submit events, admins approve them, participants register and are automatically waitlisted when capacity is hit, and the system sends confirmations, QR-code tickets, and post-event feedback requests.

The engineering brief, set by the team, was production-readiness rather than a demo: real authentication and authorization, tests that gate deployment, and a deployment path that does not depend on one laptop.

API surface

The FastAPI backend exposes 27 REST endpoints, grouped by domain. Every protected route checks a JSON Web Token and the role claim inside it.

Auth & users

Registration, login, token refresh, profile, role assignment.

Events

Create, update, list, detail; submit for approval; approve or reject.

Registrations & waitlist

Register, cancel, automatic promotion from waitlist when a seat frees up.

Tickets

QR-code ticket issuance and validation.

Notifications

Confirmation emails, ticket delivery, feedback requests after the event.

Feedback

Submit and read feedback per event.

On the numbers

The grouping above is by domain, not a verbatim route list. The count (27) and the role model are exact; ask me for the route table in an interview.

Authentication and RBAC

Login returns a signed JWT carrying the user's role. Routes declare the roles they accept, and a dependency rejects the request before any handler code runs. The three roles are deliberately narrow so that a compromised participant token cannot touch approval or admin routes.

Backend tests cover the auth dependency, RBAC rejections, the registration and waitlist state machine, and the approval workflow. Front-end tests cover the 14 React/TypeScript pages and their components. The suites run on every push; a failing test blocks the image build, so nothing untested reaches the cluster.

Deployment path

  • GitHub Actions runs the test suites, builds the Docker images, pushes them to the registry, and applies the Kubernetes manifests.
  • Nginx ingress terminates HTTPS with certificates issued and renewed by cert-manager.
  • Secrets (database URI, JWT signing key, mail credentials) are Kubernetes Secrets injected as environment variables, never baked into images.
  • Horizontal pod autoscaling keeps between 2 and 10 API replicas, so a single pod failure is invisible and a registration rush scales out.

What I would change

  1. Rollback strategy. Add image tagging by commit SHA and a documented kubectl rollout undo path with a health-check gate, so a bad deploy is a one-command reversal.
  2. Idempotent registration. A client that retries a registration request should not double-book; an idempotency key on that endpoint closes the gap.
  3. Async notifications. Move email sending behind a queue so a slow mail provider never slows down the registration response.
  4. Observability. Request logging with correlation IDs and a dashboard for registration latency and waitlist promotions.
